A few architectural constraints are worth locking down before the plan. ChatGPT is accessed programmatically through OpenAI’s API, 
so the UI can present “ChatGPT / OpenAI” as a provider while sharing the OpenAI credential infrastructure. 

DeepSeek currently exposes OpenAI-compatible and Anthropic-compatible API interfaces, which makes a provider abstraction particularly useful.

For Suno, the architecture should support it as a first-class provider but only activate cloud generation when an official/authorized API and credentials are available; 
the DAW should never depend on browser automation or reverse-engineered private endpoints. 

For MP4, remember that MP4 is fundamentally a container format, standardized separately from the codecs it carries, so your exporter should explicitly distinguish MP4 
container writing from AAC/other audio encoding.

3. File IO never runs on the real-time audio thread.

4. No unbounded allocation occurs in the real-time callback.

5. All project changes go through controlled command interfaces.

6. AI commands are validated before execution.

7. AI changes participate in Undo/Redo.

8. Project files are versioned.

9. Imported files are validated before allocation.

10. External file dimensions/sizes are never trusted.

11. API credentials are encrypted/securely stored.

12. Secrets never appear in diagnostics.

13. Cloud uploads require user authorization.

14. Audio graph changes must be thread safe.

15. Background jobs are cancellable.

16. Every visible operation reports genuine progress when measurable.

17. Every format implementation receives regression tests.

18. No third-party audio framework is silently introduced.

19. Platform-specific code stays behind abstraction layers.

20. Windows remains Delphi 12 native.

21. macOS/Linux remain Lazarus/FPC compatible.

22. Apple Silicon is treated as a first-class architecture.

23. UI controls are defined at design time wherever appropriate.

24. No production feature is represented by a stub.

25. No phase advances until its acceptance tests pass.

26. AI remains optional; the complete DAW must function without Internet.

27. Suno is optional at runtime and cannot prevent normal DAW operation.

28. Every AI provider can be individually enabled/disabled.

29. Provider APIs are encapsulated so API changes do not affect the DAW engine.

30. The system must remain usable as a serious professional audio workstation
    even if every AI provider is disabled.


===============================================================================
79. MODEL CONTEXT PROTOCOL (MCP) SUPPORT
===============================================================================

(Addendum to the AI architecture, sections 29-37 and 71-72.)

MCP is a first-class part of the AI assistance layer, NOT a new engine
dependency. It is added entirely inside the AI/tool layer behind the existing
abstractions; no audio, graph, DSP, codec, tracker or project code changes.

PURPOSE
-------------------------------------------------------------------------------

    * Let UDAW's AI assistant CONSUME external MCP servers the user configures
      (extra tools, resources and prompts) during a conversation - e.g. a
      sample librarian, a documentation server, a project-management server.

    * Let UDAW optionally EXPOSE its own safe DAW command API (section 35) as
      an MCP server, so an external MCP-aware client / local model can drive
      the DAW through the SAME validated command path a provider tool call
      uses.

    * Give the future TLocalAIProvider / local Master AI (section 72) a
      standard transport instead of a bespoke one.


ARCHITECTURE
-------------------------------------------------------------------------------

    IMCPTransport          stdio (child process) and HTTP/SSE; TLS + cert
                           validation for network transports (section 44)

    IMCPClient             connect / initialize / list_tools / list_resources
                           / list_prompts / call_tool / read_resource /
                           cancel; capability negotiation; timeouts; retries

    TMCPServerRegistry     user-configured servers; per-server enable, command
                           / URL, environment, allowed-tool allow-list

    TMCPToolBridge         maps discovered MCP tools into the AI Orchestrator's
                           tool list; every MCP tool result still passes
                           through Command Validation before any DAW mutation

    TUDAWMcpServer         optional: serves GetProjectInfo / GetTracks /
                           AnalyzeAudio / SetGain / ... (section 35) over MCP;
                           destructive tools require confirmation; off by
                           default; bind to loopback unless the user opts in

RULES
-------------------------------------------------------------------------------

    * MCP tool calls obey the AI Privacy System (section 43): no audio,
      filenames, lyrics, project names or paths are sent unless the active
      privacy mode allows it.

    * Credentials / tokens for network MCP servers live in OS secure storage
      (section 30), never in project files, never in logs.

    * MCP is OPTIONAL. With the MCP client disabled and no MCP server bound,
      the DAW and all AI providers behave exactly as before. The DAW remains
      fully usable offline.

    * An MCP server that disconnects, errors or times out never blocks audio,
      never blocks the UI, and degrades to "that tool is unavailable".

    * MCP tools are encapsulated so protocol/version changes do not reach the
      DAW engine (mirrors rule 29).

One particularly important design choice here is making AI optional rather than foundational. 
The DAW, audio graph, tracker engine, codecs, recording and DSP should remain fully operational offline; OpenAI/ChatGPT, 
Claude, DeepSeek and Suno then become provider modules connected through the controlled AI/tool layer. That architecture will 
also make adding your own local Master AI or localhost/LAN models later considerably cleaner.
